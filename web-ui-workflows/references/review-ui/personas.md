# 基于 persona 的设计测试

以 5 类不同用户原型的视角测试界面。每个 persona 会暴露出单一"设计总监"视角会漏掉的不同失败模式。

**怎么用**：挑出与被评判界面最相关的 2–3 个 persona。以每个 persona 的身份走一遍主用户动作。报出具体的危险信号——不要泛泛而谈的顾虑。

---

## 1. 没耐心的高阶用户 —— "Alex"

**画像**：对同类产品很在行。期待效率，讨厌被牵着手走。会去找捷径，找不到就走人。

**行为**：
- 跳过所有引导和说明
- 立刻去找键盘快捷键
- 尝试批量选择、批量编辑和自动化
- 被那些感觉没必要的强制步骤惹恼
- 只要哪里显得慢或有居高临下感就放弃

**测试问题**：
- Alex 能在 60 秒内完成核心任务吗？
- 常用动作有键盘快捷键吗？
- 引导能被完全跳过吗？
- 弹窗有键盘关闭方式（Esc）吗？
- 有没有一条"高阶用户"路径（快捷键、批量操作）？

**危险信号**（要具体报出这些）：
- 强制教程或不可跳过的引导
- 主要动作没有键盘导航
- 缓慢且无法跳过的动画
- 本来批量操作更自然的地方却做成一次只处理一项的流程
- 低风险动作上的多余确认步骤

---

## 2. 一头雾水的初次使用者 —— "Jordan"

**画像**：从没用过这类产品。每一步都需要指引。宁可放弃也不愿自己琢磨明白。

**行为**：
- 仔细阅读所有说明
- 点任何不熟悉的东西之前都犹豫
- 不停地找帮助或支持
- 误解行话和缩写
- 对任何标签都取最字面的理解

**测试问题**：
- 第一个动作在 5 秒内是否一目了然？
- 所有图标都配了文字标签吗？
- 决策点上有情境化的帮助吗？
- 术语是否假定了先验知识？
- 每一步都有清晰的"返回"或"撤销"吗？

**危险信号**（要具体报出这些）：
- 只有图标、没有标签的导航
- 没有解释的技术行话
- 看不到帮助选项或指引
- 完成一个动作之后，下一步含混不清
- 动作成功了却没有确认反馈

---

## 3. 依赖无障碍特性的用户 —— "Sam"

**画像**：使用屏幕阅读器（VoiceOver/NVDA）、纯键盘导航。可能有低视力、运动障碍或认知差异。

**行为**：
- 用 Tab 线性遍历界面
- 依赖 ARIA 标签与标题结构
- 看不到 hover 态或仅靠视觉呈现的指示
- 需要足够的色彩对比度（最低 4.5:1）
- 可能把浏览器缩放开到 200%

**测试问题**：
- 整条主流程能否纯键盘完成？
- 所有可交互元素都可聚焦、且有可见的焦点指示吗？
- 图片有有意义的 alt 文本吗？
- 色彩对比度符合 WCAG AA 吗（文字 4.5:1）？
- 屏幕阅读器会播报状态变化吗（加载中、成功、错误）？

**危险信号**（要具体报出这些）：
- 只能点击、没有键盘替代方案的交互
- 焦点指示缺失或不可见
- 只靠颜色传达含义（红 = 错误、绿 = 成功）
- 没有标签的表单字段或按钮
- 有时间限制且不提供延长选项的动作
- 打断屏幕阅读器流程的自定义组件

---

## 4. 有意的压力测试者 —— "Riley"

**画像**：有条理的用户，会把界面推到 happy path 之外。测试边界情况、尝试意料之外的输入，并探查体验中的缺口。

**行为**：
- 有意测试边界情况（空状态、超长字符串、特殊字符）
- 用意料之外的数据提交表单（emoji、RTL 文字、极长的值）
- 试图通过往回导航、流程中途刷新、或在多个 tab 中打开来把工作流搞坏
- 寻找 UI 承诺的与实际发生的之间的不一致
- 有条理地记录问题

**测试问题**：
- 在边界上会发生什么（0 项、1000 项、极长文本）？
- 错误状态能优雅恢复，还是让 UI 停在坏掉的状态？
- 工作流中途刷新会怎样？状态被保留了吗？
- 有没有看起来能用、却产出错误结果的功能？
- UI 怎么处理意料之外的输入（emoji、特殊字符、从 Excel 粘贴）？

**危险信号**（要具体报出这些）：
- 看起来能用、却静默失败或产出错误结果的功能
- 暴露技术细节、或让 UI 停在坏掉状态的错误处理
- 什么有用信息都不给的空状态（只有"无结果"、没有任何指引）
- 刷新或导航就丢失用户数据的工作流
- UI 不同部分中相似交互之间行为不一致

---

## 5. 分心的移动端用户 —— "Casey"

**画像**：在路上单手用手机。频繁被打断。可能网络很慢。

**行为**：
- 只用拇指——偏好屏幕底部的动作
- 流程中途被打断，稍后再回来
- 频繁在 app 之间切换
- 注意力持续时间有限、耐心低
- 尽量少打字，偏好点击和选择

**测试问题**：
- 主要动作是否在拇指区（屏幕下半部）？
- 用户离开再回来，状态被保留吗？
- 在慢速网络（3G）下能用吗？
- 表单能利用自动填充和智能默认值吗？
- 触控目标至少 44×44pt 吗？

**危险信号**（要具体报出这些）：
- 重要动作被放在屏幕顶部（拇指够不到）
- 没有状态持久化——切 tab 或被打断就丢失进度
- 本来用选择就行的地方却要求大段文本输入
- 每个页面都加载沉重的资源（没有懒加载）
- 触控目标过小，或彼此靠得太近

## 挑选 persona

按界面类型选择 persona：

| 界面类型 | 主要 persona | 为什么 |
|---------------|-----------------|-----|
| 落地页 / 营销页 | Jordan、Riley、Casey | 第一印象、信任、移动端 |
| Dashboard / 管理后台 | Alex、Sam | 高阶用户、无障碍 |
| 电商 / 结账 | Casey、Riley、Jordan | 移动端、边界情况、清晰度 |
| 引导流程 | Jordan、Casey | 困惑、被打断 |
| 数据密集 / 分析 | Alex、Sam | 效率、键盘导航 |
| 表单密集 / 向导 | Jordan、Sam、Casey | 清晰度、无障碍、移动端 |

## 项目专属 persona

如果项目提供了设计上下文（目标受众 + 品牌个性——来自项目文档、设计 brief，或用户直接给出），从受众与品牌信息中再推导出 1–2 个 persona：

1. 阅读目标受众描述
2. 找出 5 个预定义 persona 未覆盖的主要用户原型
3. 按此模板创建一个 persona：

```
### [Role] — "[Name]"

**Profile**: [2-3 key characteristics derived from the design context]

**Behaviors**: [3-4 specific behaviors based on the described audience]

**Red Flags**: [3-4 things that would alienate this specific user type]
```

只有在真的有设计上下文时才生成项目专属 persona。不要编造受众细节——没有上下文时就用那 5 个预定义 persona。
