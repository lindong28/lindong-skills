做一次整体性的设计评判——评估这个界面是不是真的能用，不只是技术上能用，而是作为一次被设计过的体验能不能成立。像一位设计总监给反馈那样思考。

流程：准备 → ① 评判 → ② 呈现 findings → ③ 向用户提问（findings 很直白时跳过）→ ④ 带优先级的行动计划。

## 模板审核分支

用户要求按模板审核或应用后的核验时，先按 [UI 规则归属](ui-rule-ownership.md) 确定范围；风格审核不默认承担通用阅读和业务审计。再通过 [manage-ui-templates](manage-ui-templates.md) 读取所选模板的当前定义与项目明确覆盖。复用项目已有的有效设计；没有时按 [manage-ui-templates](manage-ui-templates.md#本次有效设计) 在报告中明确采用的规则与覆盖。按 [组件与状态覆盖](manage-ui-templates.md#组件与状态覆盖) 核对实际组件、关联示例及展开状态，区分模板定义不足与已有规则未落实。以其有效规则、存在时的 `design_profile` 与 `acceptance` 为依据，按 [web-ui-observation](web-ui-observation.md) 真实阅读和操作目标页面，分开报告受影响操作/内容保持、模板符合及视觉效果；场景/UX 范围另报所检功能与阅读规则。对适用规则逐项交代结果、调整理由和未核实项；当前定义未规定的部分结合目标读者任务给建议，不回退旧模板标准。 整站审核对照项目页面与详情状态清单，分别核对共同视觉与页面例外；没有匹配场景不免除风格检查。核实实际覆盖和未检查入口，不把共享 CSS 或少数页面的通过外推整站。

这是本 workflow 的完整轻量分支：默认仅消费模板；明确要求来源研究时使用下节，不因缺少该站读数判模板应用失败，不自动建立下面的完整记分卡或 Nielsen 总分。用户明确要完整设计评审或项目契约要求时，再继续下文；即使用卡，模板仍可作为目标来源。只审核不实施，已授权应用中的必要修正由调用方继续完成。

审核父子场景时复用 [同一有效设计](manage-ui-templates.md#本次有效设计)，按 [单页状态与跨页旅程](batch-ui-verification.md#单页状态与跨页旅程) 分别核对页面和适用衔接；不得以批量报告完整替代旅程证据。

### 组件巡查与来源研究

复用项目现有页面、状态和核验记录，从实际渲染的组件反查模板定义；不能只遍历已经编译的规则，否则模板缺口会留在分母之外。多页与重复项复用 [批量核验](batch-ui-verification.md)，实际阅读组合关系与机器未覆盖状态。在同一报告中列出对象/状态、对应规则或缺口、证据、归属及处置；按 [四层职责](ui-rule-ownership.md) 保持风格审核范围。

| 发现 | 归属与处置 |
| --- | --- |
| 已有规则未落实 | 目标产品实现；漏编译、漏状态同时更新项目绑定 |
| 模板定义或范例不足 | 模板；说明现有 tokens 为什么不足以约束该组合 |
| 通用流程没有发现或正确处理这一类缺口 | skill；须指出执行机制缺失，不能从一次漏用直接推定 skill 需要更多规则 |
| 有依据的项目例外、范围外阅读或业务问题 | 留在目标项目并说明边界，不追加成视觉风格要求 |
| 未观察或无法核实 | 明确缺失证据，不能归为覆盖、符合或原站不存在 |

用户要求查找来源参照时，先读取 [模板来源](manage-ui-templates.md#模板来源)，只调查与缺口有关的页面和状态。使用真实浏览器核对匹配对象，分别报告直接参照、沿来源风格推导、未核实；推导可以成为设计建议，但不称为原站已有设计。可复用匹配的历史证据并注明日期；要回答当前原站状态则补现场观察。访问受阻按 [运行与依赖](portable-runtime.md) 的认证边界处理，继续不依赖原站的模板符合检查，不以公开文档代替未取得的登录态 UI。

### 修复反馈与收敛

审核与修复均对照项目既有 findings 身份和原失败条件，报告已修复、仍存在、复发、首次发现、归属迁移或未复验；没有历史记录时明确为首轮，不编造收敛趋势。已修复需同条件复验；新增规则、改变分类或缩小范围均不算关闭。只审核时在报告中给出对照，不修改项目记录。

修复按 [维护的授权边界](manage-ui-templates.md#维护) 进入 `apply-ui-template`、模板维护或通用机制修正，并更新项目同一记录。模板变动后核对本次授权范围内受影响项目的有效设计与检查绑定，再复验受影响状态；范围外消费者列为待验证，不自动跨项目改造。结果仍分模板定义、产品实现和 skill 执行机制报告，不以本轮发现条数判断整体收敛。

## 准备

开始评判之前，先知道你在拿什么标准去判：谁在用它（目标受众）、他们想做什么（用例）、它应该给人什么感觉（品牌调性），以及这个界面想达成什么。从项目文档或设计 brief 里取这些信息；那里没有的话，在进入阶段 1 之前通过 AskUserQuestion 问用户——不要假设。没有这些，反馈就是泛泛的——临床式的冷静语气对一个消费级 app 是缺陷，对一台医疗设备却是正确的。

在评判 layout、对齐、或读者要走多远才能拿到任何东西之前，先读 `${WEB_UI_SKILL_DIR}/references/web-ui-observation.md`——它定义了逐元素取值检查看不见的那个关系层、怎么去测它，以及以本次请求为 scope 的覆盖图。在阶段 1 之前从渲染出来的界面构建那张图；用它把各区域、安全的折叠、相关动作以及自然出现的状态标成 `deep review`、`adjacent regression`、`excluded` 或 `uncovered`。一次整页评判不得悄悄把自己缩成最初展开的那几个区域；一次组件评判要把其余部分清点出来，但只把请求与相邻回归面所要求的那些标成 `deep review`。

在阶段 1 之前按那份文件的「先确定有没有参照」分流。选定模板时记录其实际内容摘要和项目覆盖；用户明确要求来源研究时按「组件巡查与来源研究」追查，其余模板审核无需访问商业原站；商业产品对齐及其他有真实比较对象的任务按该档的成对观察要求执行。共用组件的其他消费者仍属于相邻回归面。

## 本 skill 产出的记分卡

每次评判之前先读 `${WEB_UI_SKILL_DIR}/references/web-ui-dimension-rubric.md`。它拥有维度集合、字段 schema、target 可以合法地来自哪里，以及逐步流程——与 `design-ui` 和 `manage-ui-templates` 共享，所以本 skill 对其中任何一部分都不另留副本。

**这次评判的产物是一张填好的记分卡**，不只是散文形式的 findings：一次交出一堆形容词的评判，交出的是一个没有失败态的东西。本 skill 是 rubric 的 `card-fill` 阶段的两个入口之一——先让 `manage-ui-templates` 跑 `overlay-resolve`，然后建卡并填卡。从 `implement` 往后归 `design-ui`，包括那次闭环的 `refill`。

诚实地填：某个维度的参照侧你无法在相同条件下测到，就记 `未取得`，而不是记一个被降级的参照。阶段 1 的维度 1，视觉套用检查，关联产品身份可辨；同一问题在那里报一次即可，不要重复计入。

本 skill 只做判断；它不提供参数。当一条 finding 的根因是视觉系统参数缺失或相互冲突时，须指出它违反的有效设计规则或造成的具体阅读、层级、操作问题；替换方案归 `design-ui` skill，在阶段 4 里点名需调整的参数与依据。根因是别的东西的 findings（信息架构、构图、微文案、情绪基调、可发现性）由本 skill 自己来指挥，而一套参数解决不了它们。

## 阶段 1：评判

从下列维度评估这个界面。各维的启发式用于定位待查对象；问题结论须关联本次有效设计、读者任务与实际影响，不从单个视觉特征或通用数量阈值直接判失败。

对每一个维度，在你下判断之前先点名那个能把它定下来的读数。读数存在、而你没有去取，就把那一侧记成 `未取得`、把该维度的 `verdict` 记成 `不判定`——用 rubric 的词汇，不要另造一套。只有维度 4 与维度 10 没有读数——情绪与语气没有数字，而编一个出来比直接判断更糟。

### 1. 视觉套用检查

对照 [视觉套用检查](review-ui/ai-slop-antipatterns.md)，检查本次任务中的具体问题。

检查视觉选择是否服务本次任务、是否符合选定风格；指出机械套用导致的具体层级、辨识或操作问题，不猜测制作来源。

### 2. 视觉层次
- 视线是不是首先落到最重要的那个元素上？你能不能在 2 秒内找到主要动作？
- 大小、颜色与位置是不是正确地传达了重要性？
- 本应有不同权重的元素之间，是不是存在视觉上的竞争？
- **到答案的距离**：点名读者是为什么来的——常常是某个组件里的一行，而不是那个组件本身——并按 `web-ui-observation.md`「测量技术」去测它。结合任务顺序、入口和导航判断这个距离是否妨碍读者取得答案；首屏之外本身不构成缺陷。核对实际数据量下的阅读路径，不从短演示外推长页。

### 3. 信息架构与认知负荷
> *任务中的认知负荷检查见 [cognitive-load](review-ui/cognitive-load.md)。*
- 结构是不是直观的？相关内容是不是按逻辑分好组？导航是不是清晰且可预期？
- 观察决策点的选项是否可分组、识别和比较，以及读者是否需要记忆不可见的信息；选项数量只作描述。
- **渐进披露**：复杂度是只在需要时才显露，还是一上来就全倒出来？
- 按该清单记录实际受阻的任务与证据，不把命中数量换算成认知负荷等级。

### 4. 情绪旅程
- 这个界面唤起什么情绪？那是有意为之且符合品牌的吗？目标用户会不会觉得「这是给我做的」？
- **峰终定律**：最强烈的那个时刻是正面的吗？体验的结尾收得好吗（确认、庆祝、清晰的下一步）？
- **情绪低谷**：检查上手时的挫败、错误带来的断崖、发现上的空白，以及高风险时刻（支付、删除、提交）的焦虑尖峰——以及设计有没有在那里介入（进度、安抚、撤销）。

### 5. 可发现性与 affordance
- 可交互的元素看起来明显可交互吗？用户在没有说明的情况下知道该做什么吗？
- hover / focus 状态有没有给出有用的反馈？有没有本该更显眼的隐藏功能？

### 6. 构图与平衡
- 这个 layout 让人觉得平衡，还是重心别扭？间距与重复里有没有视觉节奏？不对称感觉是被设计出来的，还是意外产生的？
- **留白，要量出来**：对每一个有自己标题或边框的顶层区域，外加一个有代表性的重复项，按 `web-ui-observation.md`「测量技术」表「一个区域里有多少在承载内容」一行去取它有多少在承载内容——留白是它的补集，而那份文件写明了该在哪个宽度下取。按有效设计的阅读宽度、分组和比较需求判断留白是否挤压内容或拉远相关对象；区域填充率只描述用量，不直接判好坏。没有 DOM 可测时，把那一侧记成 `未取得`、把该维度的 `verdict` 记成 `不判定`。

### 7. 作为沟通手段的排版
- 字体层次有没有告诉人先读什么、再读什么、第三读什么？各级标题之间的对比够不够？
- 正文读起来舒服吗（行长、间距、字号）？字体选择有没有强化品牌 / 调性？

### 8. 有目的的用色
- 颜色是用来传达信息的，还是只是装饰？这套调色板整体协调吗？
- 强调色有没有把注意力引到正确的东西上？对色盲用户来说，含义还成立吗？

### 9. 状态与边界情形
- **空**：是引导用户去行动，还是只是「这里什么都没有」？
- **加载**：有没有减少感知到的等待？
- **错误**：有帮助且不指责人吗？
- **成功**：有没有确认并引导下一步？

### 10. 微文案与语气
- 文字是不是清楚、简洁、有人味（而且是这个品牌该有的那种人味）？
- 标签与按钮是不是没有歧义？错误文案有没有帮用户把问题解决掉？

## 阶段 2：呈现 findings

像一位设计总监那样组织反馈。

先从覆盖图给出一段紧凑的覆盖情况陈述：哪些被标为 `deep review`，哪些做了相邻回归检查，哪些被排除、原因是什么，以及哪些留在了未覆盖状态。这是 findings 的分母，不是一个额外的评分。

### AI Slop 裁决
报告从 [视觉套用检查](review-ui/ai-slop-antipatterns.md) 发现的具体问题及其任务影响；未发现问题时如实说明，不对制作来源作 pass/fail 裁决。要残酷地诚实。

### 设计健康度评分
> *见 [heuristics-scoring](review-ui/heuristics-scoring.md)。*

按 [启发式评分指南](review-ui/heuristics-scoring.md) 先判断各项对本次对象的适用性与证据，再呈现分数或不评分的原因；汇总条件与解释沿用该指南。

### 总体印象
一段简短的直觉反应——什么有效、什么无效、以及那一个最大的机会点。

### 维度记分卡
填好的那张卡，按 rubric 的字段，每个维度一行——全局层，加上 `Scope 覆盖层` 添加的任何维度。点名本次生效的 `Scope 覆盖层`。

每一行都各自承载它对设计的后果，而一行 `不判定` 和其它行一样属于这张表。**不要从那个标签上读出一个原因**——rubric 列了四种不同的原因，而 `comparison-only` 是一种合法的模式而不是缺陷。从 `target-mode` 说出后果、说清缺的是哪一侧、以及 review 状态；只有在本该存在一个 target 而它不存在时，才把它称为 target 缺口。

阶段 1 的十个维度并不与这张卡一一对应，也不打算一一对应：阶段 1 是你怎么看，这张卡是你报什么。

### 哪些做得好
2–3 件做得好的事。要具体说出它们*为什么*有效。

### 优先问题
影响最大的 3–5 个问题，按重要性排序。给每一个打上 P0–P3 的严重度标签（定义见 [heuristics-scoring](review-ui/heuristics-scoring.md)）：
- **[P?] 是什么**：把问题清楚地点出来
- **为什么要紧**：它怎么伤害用户或破坏目标
- **怎么修**：具体的方向

一条带读数的 finding 不会悄无声息地掉出这一节。按 [heuristics-scoring](review-ui/heuristics-scoring.md) 中的任务影响判据给它定级：P0 与 P1 属于这里，P2 与 P3 连同它们的读数一起转到「次要观察」。如果 P0/P1 的集合超出了上面说的 3–5 个，就保持排序、让它长下去，而不是丢掉其中一个。

### Persona 危险信号
> *见 [personas](review-ui/personas.md)。*

自动选出与这个界面最相关的 2–3 个 persona（用选择表）。如果拿得到项目的设计上下文（受众 / 品牌），再另外生成 1–2 个项目专属的 persona。对每一个，走一遍主要的用户动作，并列出具体的危险信号——点名那些让他们受阻的确切元素与交互，而不是泛泛的描述。

### 次要观察
对那些值得处理的较小问题做简短记录。

**记住**：要直接、要具体（说「那个提交按钮」，不要说「某些元素」）。既说清哪里不对，*也*说清它为什么要紧。给具体方向，不要「可以考虑探索……」。要狠狠地排优先级——如果什么都重要，那就什么都不重要。不要软化批评。

## 阶段 3：向用户提问

呈现完 findings 之后，提出有针对性的问题（通过 AskUserQuestion），并且要扎根在**实际发现了什么**上面——绝不要问「你的受众是谁？」这类泛泛的问题。控制在 2–4 个问题，并给具体选项。如果 findings 很直白（1–2 个明确问题），且没有待用户裁决的产品取舍，就跳过、直接进入阶段 4。

已有读数呈现具体产品取舍、且适用目标尚未决定时，按 [Surface Choices](portable-runtime.md#用户选择与范围) 交用户裁决该取舍；`不判定` 标签本身不触发提问。

- **优先方向**：在发现的这几类问题里，眼下哪一类最要紧？（给出排在前面的 2–3 类）
- **设计意图**：如果发现了调性上的不匹配，那是有意为之吗——还是它应该更温暖 / 更大胆 / 更活泼？（给出能修好它的几个方向）
- **范围**：全部处理、前 3 个，还是只处理关键的？
- **约束**（只在相关时问）：有没有什么是不能动、必须保持原样的？

## 阶段 4：带优先级的行动计划

给出一份带优先级的计划。对每一项：修复方向（改什么、为什么改），并映射到它解决的那些优先问题。先按用户陈述的优先级排序，然后按影响排序——如果阶段 3 被跳过了，就只按影响排序。尊重任何已选定的范围与不能动的区域。不要指向外部命令；直接把工作描述出来，好让任何下游的 session 或 agent 都能据此行动。

把填好的记分卡连同计划一起交出去。**不要邀请用户在修完之后再跑一次评判**——rubric 的 `refill` 阶段是 `design-ui` 的交付步骤，而让用户去做它，是把一件 agent 自己能做的活推出去。明明白白地说清哪些维度回来时是 `未取得` 或 `不判定`，以及为什么；那张卡在下游没有独立的读者，所以一个没被标出来的缺口会一直不可见。

涉及期望感受、价值理解与下一步行动的对齐、模板选择、设计优化、验收或反馈维护时，先读 [体验意图](ui-experience-intent.md)，接入当前有效设计与本次任务范围；局部修正复用已有意图。
