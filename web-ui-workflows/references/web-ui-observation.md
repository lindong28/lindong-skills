# 从用户角度观察与对比网页

本档拥有网页视觉观察、关系测量与适用的响应测量方法，供设计、模板应用和 UX 测试复用。先按 [UI 规则归属](ui-rule-ownership.md) 固定应用对象及检查范围：风格检查视觉与本次引入的内容/操作回归；场景增加显式任务要求；UX 按约定任务检查通用阅读与业务。下文的观察面是可选用的方法，不因读到本文而全部变成本次验收。

通用阅读原则由 [product-ux-workflows](reading-principles.md) 拥有。视觉值相同仍可能分组/对齐错误，因此风格应用也必须观察实际组合；理解标签的角色不等于重新审计产品数据口径。

**动机案例**（真实、代价已付）：一次"1-1 复刻参照站"的任务里，我方逐值核对了 649 个 CSS 值、跑了 65 条 Playwright、拍了 100 帧对照截图、填了 700 格 rubric，全部通过；用户打开两个站一看就说日期与时间戳的水平位置不一致、缩放后观感差。实测证实：日期标签在参照站里**右对齐在时间列内**（与下方所有时间戳共一条右边界），我方把它缩进到了卡片左缘——错开 60px；≤960px 时我方内容列 564px 宽、左右留白 98/58 不对称，参照站 640px 宽、40/40 对称。**两处都在已通过的检查覆盖范围之外**。

## 按任务选择观察面

| 观察面 | 判断对象 | 适用入口 |
| --- | --- | --- |
| 视觉值 | 字体、色值、边线、圆角、图标等实际渲染参数 | 所选风格或项目视觉系统 |
| 视觉关系与结构 | 对齐、留白、分组、密度、主次、响应式；grid/flex 等机制用于解释关系 | 视觉应用与本次布局改动 |
| 内容可理解性 | 信息是否回答任务，身份、时点、单位与范围是否清楚 | [共享阅读原则](reading-principles.md)，按场景/UX 范围或本次意义回归进入 |
| 响应 | 动作到所需内容更新之间的时间、首次内容可用时间 | 用户要求、既有契约、改动影响或已观察延迟 |

看起来不对时查关系和结构；看不懂时查阅读；慢时查响应。不能用一个面的通过代替另一个面，也不从这三种问题的存在推导本轮必须检查所有面。

### 把组件放回真实布局中看

| 视觉关系 | 检查对象 |
| --- | --- |
| 主次与密度 | 实际条目数量、长名称和混合状态下，既有身份、数值与主要动作是否有清楚的视觉层级；密度按模板和用途判断，不设通用行高 |
| 分组与分隔 | 相邻容器的边框和留白共同形成清楚分组，不叠成双重边线或错误归组 |
| 标签与值 | 同角色的字号、精度展示样式、单位排版和图标一致；业务口径和数值含义保持产品定义 |
| 跨宽度与滚动 | 既有身份、时间标签、数值、状态和动作仍关联到同一对象；不被重排、裁切或滚动分离 |

明确几何、样式与状态回归用脚本批量核验；整体视觉组合仍须观察具体对象。模板应用按 [批量核验](batch-ui-verification.md#阅读结论闭合) 关联机器与人工证据，manual 不自动表示业务语义检查。

## 测量技术

| 要测的东西 | 正确做法 | 错误做法与后果 |
|---|---|---|
| 用户看到的文字位置 | 对文本节点建 `Range`，取 `getBoundingClientRect()` | 取元素盒——inline 元素收缩包裹、`text-align` 只移动文字不移动盒，两者可差数十 px |
| 某元素的几何 | 先断言它**可见且非退化**，再测。判据是**经全部祖先裁剪后仍与视口有非空交集**——`IntersectionObserver` 直接给这个读数；只查自身的 `display` 与宽高不够 | 直接测——隐藏子树里的同名元素返回 0×0 或错值，对比等于什么都没比。**只查自身属性同样漏**：实测一个 `display:block`、372×512、`getBoundingClientRect().top=266`（视口高 577）的 `<video>` 按自身属性判为"可见"，实际被祖先的 `overflow:hidden` 整块裁掉——同页 28 个播放器全部如此，且页面自己的 `IntersectionObserver` 因同一原因永不触发、`src` 从未挂上 |
| 某属性是否生效 | 读 `getComputedStyle` | grep 源码——插值生成的类名（`cls-{{ i }}`、`` `x-${n}` ``）与 `dataset.fooBar` 在源码里不以字面量存在 |
| 布局机制 | 读 `display` / `gridTemplateColumns` / 各方向 padding 的归属元素 | 只比值——同样的 64px 在"网格轨道"与"padding"里产生不同的对齐关系 |
| 留白对称性 | `left = box.left`、`right = clientWidth - box.right`，比较两者 | 只看宽度——宽度对而位置偏，用户看到的是内容没居中 |
| 一个区域里有多少在承载内容 | 量**实际绘制的那些东西**：区域内每个非空文本节点建 `Range`、每个图形元素（量条、图标、canvas）取其盒，取这些矩形的并集，再与该区域自己的盒比。高与宽分开报——前者答"下面空了多少"，后者答"一行里有多少在干活"。报数带视口，且要在**读者实际用的那个宽度**上取一次（要覆盖哪几档见本文件「必须覆盖的轴 · 缩放」）：容器有 `max-width`、或按栏分配剩余空间时，同一页在两个宽度上这个比值可以完全不同 | 拿子容器的 `getBoundingClientRect()` 当"内容尺寸"——grid / flex item 默认 `align-items: stretch`，容器被拉伸到轨道高度，于是"内容高"读成"轨道高"、空白恒算成 0。实测一页左栏 68% 是空的，按容器盒量出 **0%**；这个读数在"排得很满"与"大片空白"两种情况下取值相同，因而不是证据。反向的同形也要挡：并集里混进被拉伸的 wrapper、绝对定位的装饰、或区域外的节点时，比值趋近 1，与一个真正排满的区域读数一致——**比值 ≥0.99 时按未核实处理**，别读成"排得很满" |
| 渲染内容与它的盒子是否一致 | 比 `videoWidth/videoHeight`（图片用 `naturalWidth/naturalHeight`）与 `getBoundingClientRect()` 的宽高比；差出来的就是黑边或裁切 | 只断言盒子尺寸符合 CSS——CSS 写死的比例与产品实际输出不符时，逐元素读数**全部正常**。实测：CSS `aspect-ratio: 256/352`、产品实际交付 `256×288`，28 条片每条都带黑边（512px 高的盒子里只有 418px 是画面），而 `video=28@ready>=2` 与逐条 `videoWidth` 全绿 |
| 并排对比的两个**块级**对象共不共顶边 | 各自 `getBoundingClientRect().top` 相减 | 只比两者的尺寸——尺寸一致而起点不同，眼睛照样无法在同一水平线上比较（实测差 48px，而两个盒子都是 372×512）。**对象是文字时不能用元素盒**，改按本表第一行建 `Range`——本文件开头那个动机案例（日期标签与时间戳错开 60px）正是文字对象 |
| 一屏装得下几条 | 两道闸都过才算一条：① rect 落在**可见带**内；② 它真的看得见（没被裁掉 / 盖住 / 透明掉 / 退化成零高）。另报 `max(r.height) / band.height`，**这个 max 取未经筛选的全部条目**——高过一屏的那条必然筛不过闸 ①，而它正是要抓的。可运行配方、带的算法与仪器自检见本表下方「一屏装得下几条：用 `${WEB_UI_SKILL_DIR}/scripts/first-screen-density`，别手写」；报数带视口、缩放档与内容量 | 只用 rect 判完整可见——它给的是未经祖先裁剪的布局位置；实测被 `overflow:hidden` 裁掉、被 sticky 头盖住、`opacity:0`、`visibility:hidden`、零高的卡片全部落在带内，其中后四种连 `IntersectionObserver` 的 `intersectionRatio` 也照给 1.0（它不做遮挡命中测试、不读 opacity/visibility，零面积元素规范上直接判满）。计数于是在"看得见 N 条"与"一条都看不见"两种情况下相同（同反模式表「「DOM 里数得出来」当作「用户看得见」」）；拿 threshold 默认 0 的相交读数冒充——一张占满整屏的卡片照样计 1，`>= 2` 这类下限断言在首屏实际只剩一张时仍然通过；`max` 只取筛过的那批——高过一屏的条目筛不过边界，比值于是永远报不出 > 1，而它存在的全部理由就是抓那条；用均值守最坏形态——实测一条 998px 混进九条约 210px，均值 289 轻松低于任何按常规卡片高定的上限；分子分母不同源（边界用 `intersect(...)` 的高、分母却用 `scroller.clientHeight`）——实测把真值 2.5 报成 0.495，五倍低估；把元素数组直接喂进筛选器，或同步去读异步的 IO 结果——前者 `r.top` 取到 `undefined`、比较恒 `false`，后者拿到空集合，结果都是 `0`，与这条检查真失败时的读数逐字相同 |
| 答案元素离读者多远 | 答案元素是读者为这次访问而来的那个东西——可以是容器里的某一行，不必是页级块。从进入时的视口顶算到它，按承载它的滚动容器的高度换算成屏数，报数带视口、缩放档与内容量 | 只量到承载它的组件——组件在首屏内而目标行在其下三屏，照样通过；整页截图目测——图里没有高度基准；按距页顶算——它在定高面板里读数不足一屏，面板内却要滚很久 |
| 一次**操作**让用户等了多久 | **点击驱动的同文档交互优先用 `${WEB_UI_SKILL_DIR}/scripts/interaction-latency`**；非点击交互的测量分流、用法与已知边界见本表下方同名小节。测量遵循以下锚定纪律：跨两个时刻各取一次时间戳，**起点是他动手那一刻**：指针操作取 `pointerdown`（不是 `click`，两者之间隔着一次抬手）；滚动追加这类没有指针事件的，取触发它的那一刻（首个 `wheel` / `scroll`，或加载阈值被跨过那一刻）——起点说不出来就没有这个读数。**终点必须锚在目标节点上**：先确认**他要的那个东西已经带着新内容出现**——判据是**内容真的变了**（MutationObserver 命中后仍要比内容，同内容重渲染与 class 切换都会触发它；轮询目标选择器同理），再取下一帧。**等待要有上限**（实测取 8 s），到点未变就报"N 秒内无变化"，别挂住。报数写明目标节点是什么，带视口、缩放档与内容量，**冷、热各报一次并写明是第几次**。**首次进入**是另一回事：那一次本身就是一次导航，同一条锚定纪律照用——锚在读者要读的那个节点上，同时报告 LCP 与**读者所需内容实际可用的时刻**；先确认 LCP 对应哪个元素，壳、标题或占位的 LCP 不能代表异步数据就绪。`FCP` 与 `TTFB` 只作分段归因，别拿来回答"他等了多久"：首字节到了而后白屏三秒，TTFB 依然漂亮 | **终点不锚目标节点就等于没测。** `requestAnimationFrame` 在点击后的下一帧无条件触发，与页面有没有开始换内容无关，于是任何页面都给出约 16 ms；`PerformanceObserver` 的 `event` 条目止于**事件处理器之后的那次绘制**——handler 立刻返回、内容 1.5 s 后才回来时它照样只有几十毫秒，且 `durationThreshold` **默认 104 ms**，比它快的交互一条条目都不产生，而"零条目"与"这个 entryType 不被支持、`observe()` 静默无效"逐字同形；`long-animation-frame` 测的是 **>50 ms 的渲染帧**、不是输入到绘制的时延，不支持时同样静默为空。用 `curl` 的 `time_total`——纯客户端切换不发请求，这个读数不存在；发了请求它也只到字节收完，不含解析、执行与绘制。用 LCP / FCP 回答**站内切换**——它们按定义只在一次导航上产生，站内第二次切换永远不会有新的 LCP。只测一次就报——第二次点的是热缓存加已预热的连接，实测同一路径 MISS 0.216 s → HIT 0.086 s → HIT 0.075 s |
| 一次**等待**花在哪一段 | 拆段各取一次独立读数：网络路径（DNS / TLS / 往返）· 边缘命中与否 · origin 现算 · 传输 · 客户端解析执行与绘制。报数同上带视口、缩放档与内容量。见本表下方「一次等待要拆开才归得了因」 | 只报一个总数——它不指向任何一段，因而指导不了任何一次修改；且下一轮改完也无法归因 |

**一次操作让用户等了多久：点击驱动的同文档交互优先用 `${WEB_UI_SKILL_DIR}/scripts/interaction-latency`**

它只支持点击驱动。`input` / `change` / `select` 等交互不适用，不要用一次点击冒充实际输入；复用项目已有、覆盖真实事件与完成条件的测量。没有可复用仪器时，按本节与 [宿主与执行约定](portable-runtime.md) 做最小测量和对照，缺口如实报未核实，不要求为此扩建通用探针。

```
interaction-latency <url> --click '<被点的选择器>' --target '<他要的那个节点>'
    (--until-text '<看到这段文字才算到>' | --any-change)
    (--noop-click '<当前已选中的那一项>' | --no-negative-control)
    [--viewport 1440x900] [--timeout 8] [--max-ms N] [--json]
```

两组括号各是二选一、不能都省：不给到达判据时 loading 占位符本身就是一次"内容变了"、且能稳定很久；不给阴性对照时没有任何东西证明仪器分得清"变了"与"没变"——所以 `--no-negative-control` 把退出码**固定为 3**，不让未核实的读数以 0 的形态流到下游。

退出码：`0` 读数取到、阴性对照通过、冷热都未超 `--max-ms` / `1` cold 或 hot 任一超阈值 / `2` 仪器故障（含点击没落在预期控件上、viewport 没设成功、读数形状不对）/ `3` **unresolved——阴性对照自己报出了变化、没跑阴性对照、超时仍未到达、或目标是整页导航；不要读成 0，也不要读成通过**。夹具矩阵在上游测试（不随本包分发）。

**已知读数边界**：`--until-text` 在实际 pointerdown 前已存在时返回未核实；点击后按命中文字的 Range 与视口/祖先 overflow 裁剪相交判定到达。中间态仍可能包含该子串，两帧采样不证明业务最终态；不能区分最终内容时不作完成时延结论。`--any-change` 只覆盖文本或不可见→可见变化，不证明图片解码或资源加载完成。`--timeout` 约束每次安装/点击/采样的总预算，不含导航；超时或阴性对照导航均为未核实，不能读成页面慢。参数/viewport/异常报告的离线对照见上游测试（不随本包分发），真实浏览器量值仍须按下文做对照。

**这一行为什么也必须是程序**：与「一屏装得下几条」同因——只有真实浏览器跑得出来，而散文没有回归测试。它以散文形态被推翻过**三次**（终点判据恒为真 / 终点不锚目标节点 / MutationObserver 命中即算数），成为程序后第一版又被外部评审推翻**八条 HIGH**，而那一版的 12 条夹具对其中两条最要命的**零覆盖**：把 `location.pathname` 拼进签名，于是"点击后立刻 `pushState`、内容 800 ms 后才到"约两帧就收工；只判 `innerText` 变了而不判目标可见，于是 `opacity:0` 的目标照样算"到了"。现在各有一条会红的用例：把路径拼回签名，读数从 **850 ms 掉到 53 ms**；去掉可见性检查，那条从 exit 3 变成 exit 0 报 **34 ms**。

**操作时延读数必须先过一次阴性对照，否则按未核实处理**（工具带 `--noop-click` 时自动跑；不是加强语气，理由与那三次实测见上一段）。阴性对照的形状是**做一个不该改变任何东西的操作**（点当前已经选中的那一项），看你的仪器报不报得出"无变化"。**首屏那一支没有操作可做，因而不适用这一条**；它的等价物是**加一次已知扰动**（网络或 CPU throttle、或临时挡住首屏必需的那个资源）后重量一次，读数必须显著变大——不变就说明你没在测这一页。**别拿"重载两次、读数落在同一量级"当自检**：仪器读到缓存里的旧条目、或干脆吐一个恒定值时，两次同样一致——那正是它坏掉的样子；而仪器好的时候第一次冷、第二次热，本来就该差开（本表下一行的冷热差实测 2.5 倍）。这个自检与它要查的故障反向相关。

（实测，代价已付。环境：Playwright headless Chromium、viewport 1440×900、`https://news.aiplanet.live`、已排除本机代理；被点的是侧栏「精选」`/` 与「全部 AI 动态」`/all`。一次量法把等待条件写成"当前文档存在 FCP 条目"——该条件在点击**之前就已为真**，于是六次切换报出 25 / 43 / 59 / 77 / 80 / 101 ms 一组看着完全合理的数，而 `location.pathname` 全程未变、那几次点击**根本没换过页**。把条件改成"路径或正文首 80 字真的变了"、并加一次阴性对照之后，同一页面同一浏览器的读数变成首次 1347 ms、其后 71–95 ms，阴性对照如实等满 8 s 上限报"无变化"。**两版读数都是三位数毫秒、都排得整整齐齐**，区别只在后一版的仪器报得出失败。）

**一次等待要拆开才归得了因**

无参照时，**归因**只能靠这一节：没有对照站，你拿不到"该是多少"，但每一段都答得出"这一段该花这么久吗"。（本次已纳入响应范围时仍须测量，见「交付前的最低证据」。）

- **总数在成因完全不同的两种情况下取值相同**。1.3 秒可以是 origin 每次现算，也可以是跨洋往返，而两者一个修在代码里、一个修在部署拓扑里。（实测两侧都撞过：一次 origin 侧 `/` 的 TTFB 是 1.300 s，profile 里最大的两项各为 `_batch_related_discussions` 1.008 s 与 `_latest_run` 0.349 s——**这两项互有重叠，不要相加**；另一次总延迟的主因是 origin 在上海却被路由到美西边缘再跨洋回源，按"服务端慢"去改 region 无效、已证伪并回滚。**只看总数时这两次长得一模一样**。）
- **要一条区分度读数把候选劈开**，别靠猜。形态是**改一个只影响其中一段的输入，看总数动不动**：`limit=1` 与 `limit=40` 耗时相同（0.571 s vs 0.574 s）→ 成本是固定开销、不随行数变化，于是"数据量大"这一支被排除。
- **每一段的结论都要有阳性对照**，尤其当结论是"这一段没问题"。判边缘缓存没生效，就去找一条**确实挂着缓存规则**的路径量一次，看仪器报不报得出命中（上面那条 MISS→HIT→HIT 就是它）；量不出命中，说明这次没在测缓存。
- **在部署机上量到的 origin 耗时不是用户的等待**，它少了整条网络路径与客户端渲染。它只能用来给"origin 现算"这一段定值，不能拿去回答"他等了多久"。

**「离读者多远」与「装得下几条」的读数时点**：两者都按定义从**进入时**的视口算起，所以要在你自己这次会话的**第一次滚动之前**取；已经滚过就重载再量。豁免只给「装得下几条」比值的**分子**——最高条目可在滚动加载全量后另量，**分母仍用进入时那次的 band**（实测同一页面只滚动一次，band 从 260 变成 400、比值从 3.46 变成 2.25，两个时点混用等于这个比值没有定义）。

**一屏装得下几条：用 `${WEB_UI_SKILL_DIR}/scripts/first-screen-density`，别手写**

```
first-screen-density <url> --items '.card' [--scroller '.feed'] [--viewport 1440x900]
    [--min-visible 3] [--max-item-ratio 0.8] [--band-height <进入时那次的 band>] [--json]
```

退出码：`0` 读数取到且满足阈值 / `1` 未达标 / `2` 仪器故障 / `3` **unresolved——读数不可信，不要读成 0，也不要读成通过**。夹具矩阵在上游测试（不随本包分发）。

**这一行为什么必须是程序**：同一段量法在本文件里被写错过**四次**，四次都只有真实浏览器跑得出来，而散文没有回归测试——这本身就是本文件「自己写的机制不要让失败与成功同形」的一个实例。四次分别是：只用 `getBoundingClientRect()`（不受祖先 `overflow:hidden` 影响，被裁掉 96% 的卡片照样"在带内"）→ 用 `IntersectionObserver` v1 并声称能判遮挡（实测它对遮挡 / `opacity:0` / `visibility:hidden` / 零高一律给 `ratio 1.0`）→ 四角 `elementFromPoint`（`r.right`/`r.bottom` 是排他边界，对**正常元素**也判 false，八个夹具一律返回 false）→ band 不扣 fixed / sticky 头（实测 800 视口 + 90px 头下，一条穷举所有滚动位置都读不完整的 730px 条目算出 0.912、判"装得下"）。

**判据本身（工具实现的就是这些，你要 review 它或换个环境重写时看这里）**：

- **band** 是进入时用户实际读得到的那条带 —— 文档滚动时 = `documentElement.clientHeight` 减去 fixed / sticky 覆盖层；有滚动容器时 = 对该容器做一次 IO 拿到的 `intersectionRect`（**不是** `getBoundingClientRect()`：容器被祖先裁剪时后者把 196 报成 400，比值低估 2.04×）。band 面积为 0 时密度与比值**无定义**，报"进入时列表不在屏内"，不是报 0。
- **闸①** 是两轴完整包含，且 `intersectionRect` 要盖住整个 rect（把祖先裁剪补进来）。轴向策略在这里显式定死——不要交给 IO 的 threshold 隐式承担：实测 `threshold:[1]` 会让宽度超出视口的元素 `isVisible=false`，横向溢出页因此整页报 0。
- **闸②** 两条路径**永远同时跑**、不一致就报 unresolved。`isVisible` 保守偏 false，已实测的假阴性成因有三：相邻元素的 `box-shadow` 溢出压边（8 条报成 5，同页加 `border-radius` 即翻转）、**退化的零高兄弟节点**（相邻的完整可见条目被判 false）、祖先合成属性（`filter` / `opacity<1` / `backdrop-filter` / `mix-blend-mode` / 非轴对齐 `transform`——实测 `mask` 与 `will-change` / `box-shadow` / `contain:paint` **不**触发）。这些产出的都是**看起来合理的偏低数**，比归零更难发现，所以不能只跑一条路径再自检。
- **`max(itemHeight) / band.height` 的 max 取未经筛选的全部条目**——高过一屏的那条必然过不了闸①，只在筛过的那批里取 max，这个比值就永远报不出 > 1，而抓那条正是它存在的全部理由。
- 分子可在滚动加载全量后另量，**分母仍用进入时那次的 band**（`--band-height`）；同一页只滚一次，band 就从 260 变成 400、比值从 3.46 变成 2.25。

**交互过程中的连续性**：观察单位是一段用户行程，不只是分别打开几个 URL 或等待每一步完成。先区分本次操作应变化的区域、应保留的区域和明确要求重置的状态；导航（含整页导航）、筛选、搜索或局部刷新期间，既看目标内容何时到达，也看应保留区域有没有暂时消失、回落到默认值或移动。结束时相同，不代表中间没有打断读者。

复用 `agent-browser record` 记录从操作前到目标内容可用的过程，结合带时间的画面与 DOM / 链接 / 网络读数定位变化；`interaction-latency` 不覆盖整页导航，不能用它的 unresolved 或只有终态的截图替代这段观察。对行程中等待期间仍可操作的下一步，取一个自然的连续操作样本，核对实际到达的页面与上下文；不能先等全部加载完再声称覆盖了等待期间的可用性。报告观察过的行程、应保留区域及中途读数；录制或采样不足以辨认变化时写未核实，仪器自检按 `portable-runtime.md#证据`。

对读者会反复执行的行程，保留同一会话，沿用上述自然操作节奏（包括等待期间仍可操作的下一步）继续走若干轮，按发生顺序记录每次操作到目标就绪的耗时，分别比较首次、已预热的前段与后段；每轮重开浏览器或只报平均值不能证明持续使用仍然顺畅。若等待随使用增加，区分会话次数、数据规模与仍在运行的请求／渲染／媒体工作，并检查切走或替换后旧工作是否结束；先等这些工作结束再操作的测试不覆盖这一情形。

对仍属于当前结果的对象，另核播放位置、展开内容和输入等使用状态；正常保留与用户明确要求重置分开验证。结合前后状态与网络请求判断，不能仅凭 DOM identity 宣称连续播放。优化复用时仍须更新依赖当前筛选结果的文字和汇总。

## 先确定有没有参照

先区分本次设计依据：**模板应用／审核**以所选模板的当前定义和项目明确覆盖为规范，示例可用于理解该模板的视觉与交互，来源商业站不属于必查对象。无需因缺少商业站读数枚举候选或标记漏测；以目标真实页面验证适用规则。下文商业产品参照寻找与成对比较要求用于研究／对齐真实产品的任务。模板路径仍检查共用代码的其他消费者，且按本次应用范围执行「交付前的最低证据」第一条。确需把模板示例与目标作成对比较时，记录示例身份、内容摘要及相同观察条件，结论限定到这两个对象。

「有参照产品时的对比纪律」一节整节都写在**参照已经在场**的前提下——用户点名了某个站，或任务本身就是复刻。但参照常常没被点名却近在手边，而**没人会来告诉你它在**。判据是**它为同一个问题做过一遍决策、而那些决策已经过真实使用的检验**——按这条，同一产品的另一条轨、另一个租户、上一版页面、同一设计稿的移动端实现、同一组件在另一条产品线的落地，都算。同仓已交付的那种往往比外部站更强：它已经被人用过、问题已经被人提过，而且它的取值就是同一套代码在另一组输入下的正确答案。

判定“本次没有参照”前，按 [evidence-sufficiency.md「发现候选的检索」](portable-runtime.md#证据) 查找并报告检索读数；按本节的参照判据逐个给出候选结论，覆盖下述共用代码的第二个消费者。

**共用代码的第二个消费者是最危险的一种**，单独列出来：一段为第一个消费者写的逻辑，会把那个消费者的语义当默认值编码进去；换一组输入就静默变味，而两边跑的是同一份代码，diff 里什么都看不出来。判据不是"我改了什么"，是"同一段代码在两组输入下各产出什么"——只能在两侧各跑一次读数来比。

（实测：一处"哪几档默认展开"的判据按 scope 档名写死。第一条轨有两档命中，每张卡片 81 个可见读数；第二条轨的指标全落在另一档，同一段代码给出 **0** 个——页面上一个数字都没有，而那一页存在的理由就是核对这些数字。改动它的那几次提交里，没有一行 diff 指向这个后果。）

本节判两件事，一个成立不蕴含另一个。全 harness 只在这里定义它们，别处一律按这两个名字引用：

| 谓词 | 判据 | 它开启什么 |
|---|---|---|
| **值得比较** | 上面那条——它为同一个问题做过一遍决策、而那些决策已经过真实使用的检验 | 下一节整表，含「独有元素交用户裁决」 |
| **参照位资格** | 本次选定、可实际观察的比较对象；商业原站对齐使用那个真实产品，模板示例比较使用当前模板关联示例 | 可占 `measurement` 的 reference 侧，读数只支持该对象的结论；模板定义中的规范目标另走 rubric 的 `所选模板` 来源 |

**判「值得比较」不成立，关掉的是「逐个清点我方独有元素、每个都交一次「移除 / 保留」」这条系统性入口**——下一节那一行是它唯一的来源，而 rubric 的维度集产出不了那条裁决（边界见该档「本档拦不住什么」）。**关掉的不是整类问题**：属于本次范围的发现仍按交付与选择规则处置。风格任务中发现的范围外基线内容问题单列，不因此把视觉审核扩为逐项内容去留裁决；完整 UX/内容评审按其覆盖图观察。

**「值得比较」成立而「参照位资格」不成立是常态**：一个没被点名但在跑的同类产品值得你逐项比过去，却不该拿它的实测值给本页设目标。此时下一节整表照跑、读数进 findings；它**不能给本页设任何目标值**，而它的「缺少某元素」这条读数**只生成待裁决项，不生成判定、也不触发任何自动动作**。`measurement` 的 reference 侧此时记 `无参照位`（取值定义见 rubric）。

**两个谓词都要留下可重跑的读数**，否则「判过为假」与「根本没判」只留同一个 token——那正是本节要防的那种失败。上面那条枚举要求（候选、逐个查过、各自结论）就是「值得比较」这一侧的读数；「参照位资格」这一侧的写法见 rubric 的「reference 侧的三态」。

**这只让读数存在，不让缺席被拦住**：没有任何节点负责检查它写没写，「整段没执行」与「执行了但漏写」仍表现相同。要关上这一支得有一个流程外的观察者，本 harness 目前没有。

**命中一个已不可运行的对象时**（下线的上一版、已停用的租户）：凡结论依赖当前 live 状态的纪律，此时**无法执行**——逐项报「未核实」并写明原因（下一节开头写的就是「参照产品**在跑时**」）。**不要写「不适用」**：那个词表示这一项没有对象，而这里对象是有的、只是取不到 live 证据；混用会重新打开静默跳过的口子。也不得拿静态快照、截图或抄录清单顶替——冻结快照保存的是**历史观察**，不替代当前 live 观察。

## 有参照产品时的对比纪律

参照产品在跑时，它**本身就是规格**，任何抄录出来的中间清单都只是它的有损投影。

| 纪律 | 内容 |
|---|---|
| **同条件成对测量** | 权威检查是"同一次运行里，把两边放在**同一 viewport / 缩放 / 主题 / 交互状态**下各测一遍再比差"。拿我方对着抄录清单核对，可以全绿而两边仍然不同——因为清单可能本身就漏 |
| **时间维度的同条件** | 上一行列的同条件（viewport / 缩放 / 主题 / 交互状态）只够静态面用。比响应还要另外控住三件事，**每件都要落成读数，不能只写"已控住"**——那句话在认真查过与压根没查两种情况下逐字相同（同本档「先确定有没有参照」那条）。**测量点**：两边都从用户那台机器量，不是各自的部署机；读数是**每次请求各报一次 TCP 连接耗时**——`curl` 里点名 `%{time_connect}`，**不是 `%{time_appconnect}`**：实测那次事故里两个字段朝相反方向读，`time_connect` 恒为 `0.000`（露馅）而 `time_appconnect` 恒约 1.0 s（看着完全正常），取后者的话这条检查在它自己的原始证据上就会通过。判据是它接近 0 而对端在另一个大洲——**但 `0.000` 另有成因**（`file://` 传输同样给 `0.000000`），所以它是一条提示而非判决：同一命令加 `--noproxy '*'` 重跑一次比对才算数（那次 TTFB 从 2.5 s 变成 0.12 s，整张表作废重来）。**缓存冷热**：两边各冷一次热一次，报数写明是哪一次。**网络路径**：报出两边各自解析到的 IP 与边缘节点标识（`eo-cache-status` 一类的响应头），两站 origin 不在同一地理位置、或一边过 CDN 一边不过时，你量到的差可能整个来自往返距离而与代码无关。控不住或读不出的那一项写"未核实（差在哪一项）"，别把差值当成我方的缺陷 |
| **反向完备性** | "我写的每个值都有出处" + "清单每行都忠于参照" 仍漏第三个方向：**参照里有、清单里没抄的规则**。范围内的每个参照组件，要从参照侧枚举其规则，逐条确认我方有对应决策（已实现 / 有理由的接受差异）。缺失的规则在前两个方向上完全不可见 |
| **独有元素交用户裁决** | 上一行只覆盖"参照里有、我方没抄"。反方向——**我方有、参照没有**——在从参照侧枚举规则时结构性不可见：参照侧没有这个东西，枚举不到它。所以范围内每个我方独有元素都要反过来记一条决策：参照在同一位置什么都不放，那是它做过的取舍，不是它的疏漏。默认动作是把「**移除 / 保留**」二选一按 `CLAUDE.md`「Surface Choices」交用户——"缩小、换个视觉语言重塑、移到次要位置"都属保留的子形态，选它仍要先回答留不留，agent 自行挑一个折中不算已处置（executor 是子代理时按 [宿主与执行约定](portable-runtime.md)的两跳：子代理列出这些元素并标注待裁决，caller 履行 surface） |
| **结构先于值** | 先比布局机制（grid/flex、列数、轨道、padding 归属），再比值。机制不同则值再准也对不齐 |
| **叠加而非并排** | 两张图并排放，人眼与模型都测不出 60px 偏移。用差值叠加（difference blend），或算逐行/逐列的墨迹分布曲线再比峰位 |
| **别把参照当唯一真相之外的东西** | 参照站会漂移。要冻结快照并记录哈希；但**冻结的是像素与 CSS，不是"我抄对了"的结论** |

## 先画本次请求的网页观察覆盖图

判断页面之前，先从**真实渲染页面**列出本次请求的观察分母；不要从实现文件、测试名或已经打算检查的项目反推。覆盖图至少包含顶层用户可见区域、区域内的安全展开内容（safe disclosure）、会改变这些区域答案的显式控件，以及沿本次使用路径自然出现的异步状态。折叠内容仍在分母里，不能因为默认不可见就静默消失。

| 用户请求的范围 | 怎么筛选覆盖图 |
|---|---|
| 应用整站/整页视觉风格 | 各可见区域及有关状态按视觉规则深查，共享组件的实例由完整清单绑定；不追加所有区域的业务审核 |
| 评审、优化某个 URL / 页面「展示的信息」或整体体验 | 每个承载内容的顶层可见区域都是**深查候选**；不深查的逐项写出与用户目标相关的排除理由 |
| 评审、修改一个具名组件 | 深查该组件、其安全展开内容与自然状态，以及用户完成这次判断所依赖的内容；共享 renderer / layout 的消费者做**相邻回归**；其余顶层区域仍先列出，再说明排除 |
| 只代用户完成浏览器操作，不判断页面内容或可用性 | 不触发本覆盖图 |

覆盖图里的每一项落到四种处置之一：**深查（deep review）**（按本次应用对象选定的观察面检查）、**相邻回归（adjacent regression）**（只核本次改动可能波及的关系）、**排除（excluded）**（有与目标相关的理由）、**未覆盖（uncovered）**（需要破坏性操作、构造当前路径不会自然出现的状态，或受工具 / 权限限制）。深查区域里的安全展开内容要在默认态与展开态都读；纳入内容阅读且使用 `page-repetition` 时，运行形态也要包含这些展开内容。

这张图不是全量 QA 矩阵。只操作会改变深查项可见答案的控件；同一组范围 / 筛选值按**不同渲染语义**取代表，不做无差别笛卡尔积；不主动触发删除、支付、提交等破坏性动作，也不为普通检查伪造罕见空态 / 错误态。需要多 persona、跨状态正反路径或产品级可操作性结论时，升级到 `test-ux`，不能用这张图代替。

交付读数时同时列出深查、相邻回归、排除与未覆盖项。覆盖图是后续结论的分母：只报告「检查了哪些」而不报告其余项去了哪里，在完整覆盖与漏掉一个折叠区域时输出相同，不构成范围证据。

## 必须覆盖的轴

**缩放要兑现大小与密度的取舍**（用户 2026-09-09 明示）：用户放大是为了看清图片、文字等内容，缩小是为了在同一窗口面积看到更多内容。设计与验收都要检查主内容区是否兑现这两个方向；导航栏仍按其用途与既有响应式规则处理。固定列数把缩放抵消为卡片伸缩、实际可见大小与密度基本不变时，即使没有溢出也属于体验缺陷，在「构图与响应式」维度扣分 / 判未达成。

对本轮覆盖图中的布局 / 缩放验收，默认在同一内容、同一窗口取缩小（<100%）/ 默认（100%）/ 放大（>100%）三档，记录主内容的屏幕可见尺寸与每行 / 可见区域的条目数量。具体档位按使用场景与布局变化区间选取；网格要观察跨列数变化的区间，不要求每一小档都换列。用 CSS 视口模拟浏览器缩放时明确标注模拟，并将 CSS 尺寸乘缩放倍数后再比较屏幕可见尺寸；仅改变 DPR 或 pinch zoom 不代表页面缩放后的重排。

| 轴 | 要求 |
|---|---|
| **缩放** | 浏览器放大在窗口物理尺寸不变的前提下缩小 CSS 视口：缩放倍数为 z 时，视口宽约为 W/z。除上述三档外，检查本次受影响断点两侧的布局；需要时可用 B-1 / B+1 取点，不能只取整数缩放档而跳过相关布局区间。精确断点 B、更多缩放档位由适用项目契约、任务要求或已观察到的缺陷触发，不默认遍历无关断点。报告实际档位、断点与未覆盖范围，不把取样通过称为全档覆盖 |
| **交互状态** | 沿读者行程实际导航、展开、筛选、搜索、滚动或折叠，记录布局与实际操作结果；本次范围含响应时测时间，并按「交互过程中的连续性」观察过渡过程。参照产品的对应状态要同步触发再比 |
| **主题** | light / dark / 跟随系统三态各比一次；有的差异只在一种主题下出现 |
| **内容量** | 空态、单条、满屏、超长标题。参照站与我方内容不同时，比的是骨架与关系，不是文本 |

## 条件式验收：缓存升级（N-1 暖缓存→N 普通重新加载）

本节只在验收一次网页发布或版本升级时进入；单纯观察、评审或修改当前页面时不加入覆盖图，也不输出固定槽位。`N-1` 是升级前发布，`N` 是本次发布；普通重新加载是用户触发浏览器 Reload，且不清缓存、不用 hard reload、不开 DevTools Disable cache。响应版本身份是能区分 N-1 与 N 的消费者侧读数，如浏览器实际响应的内容摘要或 build marker。

触发条件是：N 复用 N-1 已发布的浏览器缓存键或缓存变体，响应字节或缓存策略发生变化，且旧响应可能继续被使用。这里的键包含会区分缓存条目或变体的 URL、请求与缓存分区条件；同一 origin / path 本身不能证明命中了同一缓存条目。无法判清键、变体或中间层行为时进入本节并报 `uncovered`，不能判 `n/a`；确定没有风险资源时才报 `n/a`，并写明资源为何换了键或旧响应为何不可复用。

按下面的顺序取得读数；任一步不能建立时，不得用只在 N 创建的全新浏览器配置档所得的冷启动读数替代。

1. **建立 N-1 暖缓存。** 在受控、持久的浏览器配置档中加载 N-1，记录配置档身份读数、受测缓存键或变体、N-1 响应版本身份与缓存策略。再做一次普通重新加载，用能区分暖缓存与冷请求的浏览器网络 / 缓存读数，证明该条目被缓存命中、重新验证或以其他可复核方式实际参与；只写“已暖缓存”不算证据。
2. **切换到 N。** 让同一隔离入口提供 N，在同一浏览器配置档中普通重新加载。重读配置档身份，并取得能区分旧条目参与、重新验证与纯冷请求的网络 / 缓存读数；配置档身份、缓存键或变体不连续，或浏览器不提供有区分度的读数时，结果是 `uncovered`，不是 `pass`。
3. **核验消费者结果。** 响应字节变化时，从浏览器实际加载的响应读取 N 的响应版本身份；只读 origin 文件或上游响应不算。只改缓存策略而响应字节不变时，证明这次普通重新加载发出了请求或完成重新验证，并从 N 响应读取生效策略。
4. **给出四态结论。** 链路与消费者读数完整且到达 N 是 `pass`；链路完整但仍得到 N-1 字节或旧策略是 `fail`；确实尝试后因缺少环境、能力或有区分度的读数而不能建立链路是 `uncovered`，同时写出试了什么、撞上什么；触发条件确定不成立才是 `n/a`。

无需也不应接管用户的日常浏览器配置档。Chrome Dev、自动化浏览器或其他隔离配置档只要从 N-1 暖缓存连续复用到 N，都可提供有效读数。不得仅为构造证据回滚生产；已有隔离环境时可在同源入口依次提供 N-1 与 N，没有时先报 `uncovered`，是否新建或重配隔离部署须作为有成本和状态影响的用户选择交其裁决。

## 交付前的最低证据

**一、在声明范围内实际用一遍。** 有无商业参照不改变这条要求。先给覆盖图，再报告具体观察对象、状态、读数与未覆盖部分；单元素参数、截图数量与“已读过”不能替代实际判断。

| 本次范围 | 最低交付证据 |
| --- | --- |
| 风格应用 | 适用规则的视觉值与组合关系，实际宽窄屏/相关展开状态；真实操作受影响控件，核对既有内容与操作没有因本次改动回归。未纳入业务审计应明确说明 |
| 场景应用 | 风格项及场景显式声明的信息、交互与阅读要求；按 [共享阅读原则](reading-principles.md) 给出具体读者判断 |
| UX / 内容审核 | 约定任务的答案是否可取得、在哪里、经过哪些操作；相应业务与阅读结果，适用时引用产品事实 |
| 纳入响应测量 | 按「测量技术」测动作至目标内容更新的秒数，标明冷热和次数；首次进入另报所需内容可用时刻及 LCP，不能用静态截图或“流畅”替代 |

问题和未核实项逐项交代，修复本次造成的回归；范围外基线问题单列归属与去向，不吸收成风格违规。有限内容按任务取样，既不要求无限列表从头读到尾，也不把抽样外推完整状态覆盖。批量报告只证明固定分母内的声明规则，规则编译及页面清点完整性另核。

**二、实际比较两个运行页面时做同条件对比。** 固定模板应用不要求访问来源商业站。用户要求真实原站对齐或主动比较模板示例时，记录双方身份、版本、相同视口/缩放与对应状态，逐屏观察并对有关元素测关系；响应属于本次比较范围时双方同条件计时。示例不能替代目标产品读数，任一未观察面保留未核实。

页面用途包含索取评价时，另按 [反馈回收验证](portable-runtime.md#用户反馈与交付) 实际核对选择、修改及整份复制 / 保存后的结果；播放器与元素探针不能替代这条路径。

## 页面交付的证据记录

本节承接共享取证规范的页面交付要求，按本文的任务范围分流执行。

- **交付一个用户会打开的页面时，报告正文必须带该 URL 的验收读数行**——形如 `page-acceptance <url> --expect 'video=28@ready>=2' → ever_intersected 28/28, ready_ok 28/28, errored 0`（`${WEB_UI_SKILL_DIR}/scripts/page-acceptance`，它把上面那层替身变成一条机械读数）。`--expect` 要写的是**这一页的主功能元素**，由用途决定，不由本轮改动决定。这条约束的强制力来自读者：**缺了这行、或行里的 URL 与你交出去的对不上，用户一眼可见**——这是把"我可能忘了查"从静默失败改成可见缺失，而不是又一条只能靠自觉的规矩（它确实**不是**机械闸：无人阻止你不写，正因如此才要让它的缺席显形）。跑不了探针的场景（生产 URL 不得被滚动扫描打扰、页面需登录态等）改为写一行降级声明，说明未核实与差在哪一层。
- **交付的页面用途是"人读到结果"时**，探针打印的「不覆盖」按[取证的充分性](portable-runtime.md#证据)「你消费的任何报告里，任何你没自己取过的读数」那条处置——这一页要落进待办的具体是哪些项：**"探针全绿而读者看不见"的那些**，遮挡、透明度、visibility 与关系层对齐同属此类（同行的可读性归下面「别把可读性归成"打磨"」那条，感知质量归 [多模态自评与人评升级](portable-runtime.md#视觉与阅读)，两者都不按待办处置；「内容对读者有没有用」归下文「页面验收的观察面由任务范围决定」；`可操作性` 与「多状态真实使用」由探针自己的 `NOT_COVERED_OWNERS` 判给 `test-ux`，不进本条的待办；探针也会打印「响应（点下去到画面更新等了多久）」，它归下文「页面验收的观察面由任务范围决定」中的响应项、同样不进本条的待办）。探针覆盖的是存在与就绪，而这些与功能同级：读者要的东西离他几屏、进入时的那一屏装得下几条完整的、要被并排比较的两个对象共不共基线、渲染内容与它的盒子是否一致、每个区域里有多少在承载内容、以及元素有没有被盖住或透明掉（本枚举里不适用于这一页的项写 `n/a(<这一页的主内容形态>)`，别硬填也别留空——裸一个 `n/a` 在"确实不适用"与"没量"两种情况下同形）——任一不成立页面就没做到它被建出来要做的事，而它们在探针读数上**全部与正常同形**。所以**与验收读数行（或它跑不了时的降级声明）同段**再写一句 `可见性与关系层：<各一句读数>` 或 `可见性与关系层：未核实（<差在哪一项>）`——缺了这半句与缺验收行一样一眼可见，理由同上一条。**探针跑不了不等于这一层跑不了**：「离几屏」与「一屏装得下几条」依赖进入时的视口（时点见 `web-ui-observation.md`「测量技术」表下那条脚注），其余几项不需要滚动。量法见 `web-ui-observation.md`「测量技术」。实测代价：CSS 写死的 `aspect-ratio` 与产品实际输出不符时逐条读数全绿、28 条片每条都带黑边，并排两个播放器顶边差 48px，第一个视频在 5.94 屏之外——三样都通过了验收行（数字见 `web-ui-observation.md`「测量技术」）。
- **页面验收的观察面由任务范围决定**：按 `ui-rule-ownership.md` 分流，按 `web-ui-observation.md`「交付前的最低证据」给具体读数。风格应用核视觉与本次引入的内容/操作回归；场景核显式信息与交互要求；UX/内容审核核约定任务中的通用阅读。纳入阅读时报告“内容对读者有没有用”的具体判断，阅读原则 owner 为 `reading-principles.md`；纳入响应时另报动作至目标内容更新的时间。范围外基线问题单列，不能被风格通过吸收。工具的 NOT_COVERED_OWNERS 是方法归属，不自动扩张检查范围；已纳入范围却测不到的项按上述出口报未核实。
- **用途是"给人看"的页面，别把可读性归成"打磨"**——归错了它就不进验收项，这正是那次 `aspect-ratio` 黑边 / 顶边差 48px / 第一个视频在 5.94 屏之外的成因。判据用 [宿主与执行约定](portable-runtime.md)那条：能否语义追溯到用户表达的目标**或约束、或本任务开始前已生效且适用于该环境的契约**（三者取一，缺了后两项会把本该算功能的重新判成非功能）。据此：可读性、答案可达性、并排对象的可比性属**功能**，不合格即交付物没做到它要做的事，不需要问用户；而可读之上的精致程度（字阶档数、圆角族、过渡时长）属非功能，按同一条规则测出来 surface 成 choice，不默默做也不默默跳过。

## 反模式

| 反模式 | 为什么错 |
|---|---|
| 商业原站对齐只检查抄录清单 | 原站对齐的对象是实际产品，清单漏掉的规则仍需从原站观察；模板应用则以已选模板定义为规范，是不同任务 |
| 只做单元素值断言就宣称视觉对齐 | 值全对而关系错是最常见形态，且正是用户第一眼看到的 |
| 测元素盒当作测文字位置 | inline 收缩与 `text-align` 使两者相差数十 px |
| 不校验可见性就测量 | 隐藏子树里的同名元素给出 0×0 或另一套值，对比静默失效 |
| 「DOM 里数得出来」当作「用户看得见」 | 元素计数在"渲染正常"与"被祖先整块裁掉"两种情况下取值相同，因而不是证据。它骗过自己的方式很特别：人已经打开了页面、也确实在查询真实 DOM，于是产生"我已经站在消费者通道上了"的满足感——而通道之内还分着层 |
| 并排看图找偏移 | 人眼与模型都不可靠；要叠加或算分布 |
| 缩放只取整数档 | 断点中段（如 641–960 的中部）被整档跳过 |
| 一致性断言当合理性断言 | "A 与 B 一致"对"A、B 同错"完全免疫（如 VOL 日期与报头日期都是未来日期而一致） |
| 用 rubric 格子的绿色代替看过 | 判定若来自别处证据，就要写明来自别处；标成"看过"即虚报 |
| 拿"打开这一页"的读数当"用这一页"的读数 | `time_total` / TTFB / LCP / FCP 全绑在**一次导航**上，而用户抱怨的动作是站内切换、筛选、展开——它要么不产生导航（读数不存在），要么从不在被观察的动作集合里。两种情况下这些指标都全绿，与页面真的很快时逐字相同。（**首次进入那一次不在此列**：它本身就是一次导航，**LCP 只有落在所需内容上时才能代表可读时刻**；异步数据页另取目标内容就绪读数——`FCP` 与 `time_total` / `TTFB` 仍只作分段归因，理由见「测量技术」那一行。被禁的是拿这四个去回答站内的后续操作。） |
| 报一个总延迟数就动手改 | 总数在成因完全不同的几种情况下取值相同（origin 现算 / 跨洋回源 / 边缘未命中 / 客户端渲染），它指导不了任何一次修改，改完也归不了因。先拆段，再对可疑的那段取一条区分度读数 |
| 只量一次就报延迟 | 第二次点的是热缓存加已预热的连接。实测同一路径 MISS 0.216 s → HIT 0.086 s，冷热差 2.5 倍；不写明是第几次，这个数就没有定义 |
