# 阅读档实例 —— 长篇技术文档

一套完整指定的视觉系统，面向那些**从头读到尾**的文档：交付报告、设计文档、复盘、运维手册、内部说明。结构与 [`reference-instance.md`](reference-instance.md) 相同，取值不同——那份文件针对的是 11–13px 的 dashboard 与控制台，用在一整页散文上会很折磨人。

意图：一个读者、一列、连续阅读若干分钟，其间穿插着表格与代码。分隔仍然来自**线条与色调**，不是阴影。密度要松到让一个段落读起来不像一行日志。

不适用于：dashboard 与后台管理界面（用 `reference-instance.md`）、营销页，或任何读者是在扫而不是在读的东西。

参数依赖沿用 [design-ui 的 L2 参数推导顺序](../design-ui.md)，改变上游取值时重算受影响的派生值。这里只重述与 `reference-instance.md` 不同的那些取值；§9 为位于被替换 ramp 之下的每一个参数记下一个 disposition，而 colour roles **不**在直接沿用之列——§8 替换了它们。

## 1. 基准单位与 spacing ramp

基准单位 **4px**，与参考实例相同的闭合梯子。变的是每个角色从哪一档取值——一份文档要比一个控制台松上一到两档地呼吸。

梯子本身就是 `reference-instance.md` §1，未作改动——九档全在，取值相同。只有角色→token 的映射不同，所以只重述这一部分：

| Token | 在文档中的用途 |
|---|---|
| `--sp-2` | 一个磁贴内部从标签到取值的间距 |
| `--sp-3` | 列表项之间的分隔 |
| `--sp-5` | 表格单元格的 padding |
| `--sp-6` | 段落下外边距、callout 的 padding |
| `--sp-7` | 卡片 padding、节内节奏 |
| `--sp-8` | 页面外壳顶部 |
| `--sp-9` | **节与节之间** |

没有列出的 token（`--sp-1`、`--sp-4`）仍然存在；只是它们不承担任何文档特有的角色。

## 2. Type ramp

每一档都带自己的 line-height、字重与 letter-spacing。**正文 line-height 是与控制台实例之间最大的一处差别**：16px 文字上是 26px，而那边是 13px 上 18px。

字重：**400** 正文 · **500** UI 标签 · **600** 标题。

| Token | 字号 / line-height | 字重 | Letter-spacing | 用途 |
|---|---|---|---|---|
| `--t-eyebrow` | 12px / 16px | 600 | `+0.08em`，uppercase | 节引题、nav 标题 |
| `--t-micro` | 13px / 20px | 400 | normal | 元数据行、脚注 |
| `--t-small` | 13px / 19px | 400 | normal | 表格子标签、提示 |
| `--t-table` | 14px / 22px | 400 | normal | 表格单元格 |
| `--t-body` | **16px / 26px** | 400 | normal | 默认文字 |
| `--t-label` | 14px / 22px | 500 | normal | nav 链接、按钮 |
| `--t-h3` | 16px / 24px | 600 | normal | 次级标题 |
| `--t-h2` | 20px / 28px | 600 | `-0.01em` | 节标题 |
| `--t-h1` | 28px / 36px | 600 | `-0.01em` | 页面标题 |
| `--t-display` | 24px / 32px | 600 | `-0.015em` | KPI 取值 |

**Measure**：散文与列表限在 **74ch**。表格、卡片与代码块占满整列——这个上限管的是*文字行长*，不是容器宽度。搞反了，就会在宽屏上做出一个两侧留着空槽的 1100px 页面。

**最隐蔽的一种搞反方式是两列 grid**，因为这个上限*确实*加在文字上——只不过它一次加在了两段文字上。实测：`.kv{display:grid;grid-template-columns:auto 1fr;max-width:74ch}`，一个标签/取值列表。`auto` 的标签列吃掉了 **710px 中的 350px**，剩给取值列的只有 **35.8ch**——不到它预期 measure 的一半——于是这个块在第一屏上渲染成了一条又高又窄的带子，旁边是一片空洞。这个上限在样式表里看起来是对的，在页面上却是错的。

自己重新推导一遍，而不是把这些数字当成可信的——这些读数属于一个页面，不属于本文件。对着 `video-eval-arena` 的 `arena/static/rt-delivery-report.html`，在 `889c870` **之前**的那个 commit、1920×1080 下：`getComputedStyle($('.kv')).gridTemplateColumns` 返回这两列的宽度，而 `ch` 值就是那个宽度除以该元素自己计算字体下一个 `0` 的宽度。

把上限加在每一列文字上，不要加在它们的容器上：`grid-template-columns: minmax(0, 20ch) minmax(0, 74ch)`，grid 上不加 `max-width`。两列都用 `minmax(0, …)` 而不是 `auto` / `1fr`——后两者的自动最小值是 `min-content`，于是一个不可断行的 token（一个 URL、一个标识符）就会把这一列顶出 viewport，而这件事只有在窄宽度下才会显露出来。

**一般形式**：一个 measure 作用于*一段文字*。只要有 N 段文字共享同一个上限，每一段拿到的都少于那个 measure，而且没有一段等于你写下的那个数。去读计算出来的列宽，不要读那条声明。

**字体**：一款带等宽数字的正文字体，外加一款配套的等宽字体用于标识符与代码。当这份文档必须是一个单独的离线文件时，webfont 无法廉价地内嵌进去——用一套精选过的系统字体栈，而不是一个光秃秃的 `sans-serif`，并且如果文档里有 CJK 文字，就把 CJK 字体显式地列进去。

## 3. Density

| Token | 取值 | 作用于 |
|---|---|---|
| `--pad-cell` | `12px` | 表格单元格与表头——文档里的表格是被读的，不是被扫的 |
| `--pad-card` | `24px` | 卡片、callout、摘要面板 |
| `--pad-page` | `0 24px` | 页面外壳 |

`--h-control` 与 `--h-row` **不**从控制台实例继承。那份文件说控件高度由它的 line-height 加上垂直 padding 推出，而这里的 type ramp 变了：`--t-table` 的 22px 加上 `--pad-cell` 的 12px，已经把一行推到 46px，所以它那个 `--h-row: 32px` 站不住。从本实例的 ramp 重新算出这两个值，而不是照抄它们。

## 4. Motion

| Token | 取值 |
|---|---|
| `--dur` | **140ms**——比控制台的 120ms 略慢；文档里的交互是从容的，不是连珠炮式的 |

`--ease`、`--t-state`、可 transition 属性的白名单以及 `prefers-reduced-motion` 分支，都是 `reference-instance.md` §6，未作改动。

## 5. Layout

本实例独有；控制台实例没有对应项，因为一个 dashboard 按定义就填满它的 viewport。

| 参数 | 取值 | 为什么 |
|---|---|---|
| 容器 | `max-width: 1560px` | 一个约 1100px 的居中容器，会在 1600px 的屏幕两侧各留下一条很宽的空带 |
| 侧边 nav | `190px` 固定 | 为分节文档提供的锚点导航 |
| 间隙 | `--sp-8`（32px） | |
| **正文占比** | 宽屏下 **≥ viewport 的 70%** | 「内容拿到宽度」这句话的可测形式。去验证它；不要用眼估 |
| 折叠 breakpoint | 860px | 低于它时，nav 变成内容上方的一张卡片 |

两种值得写出来的失败形态，因为它们都是静默的：

- 一个 `1fr` 的 grid 列会**从内容的 min-content 取它的自动最小值**，于是一个不可收缩的子元素就把整列顶出 viewport。用 `minmax(0, 1fr)`。
- 一条放在它所覆盖的规则**之前**的移动端覆盖规则，在特异性相同时会输在源码顺序上。media query 块应该放在它要修改的那些规则之后。

## 6. 文档 affordance

控制台一个都不需要；一份要通读的文档全都需要。

| Affordance | 要求 |
|---|---|
| 锚点导航 | sticky 的侧边 nav（窄屏时改为 sticky 顶栏），并标出当前所在的节。以 viewport 高度约 25% 处的一条线来判定高亮，而不是顶边，否则一个长节会在还没滚走之前就失去高亮 |
| 渐进披露 | 深层内容用 `<details>`。默认收起，而且**那行 summary 必须能单独读懂**——读者不打开就应该知道里面是什么 |
| 代码块 | 能整块复制。`navigator.clipboard` 在安全上下文之外不可用，而 `file://` 不是安全上下文——所以一份打算以文件方式打开的文档需要一个回退：选中文本，并把这件事说出来。没有它，那个按钮会静默地什么都不做 |
| 宽表格 | 包进一个 `overflow-x: auto` 的区域，并让它**可用键盘聚焦**（`tabindex="0"`、`role="region"`、一个 `aria-label`），而且只在该区域确实溢出时才告知可以滚动 |
| 状态 | 带文字标签的 badge，绝不只靠颜色 |

## 7. 可访问性下限

通过测量计算出来的颜色来验证，不是靠意图。

| 检查项 | 下限 |
|---|---|
| 正文与次级文字在它们各自的背景上 | 4.5:1 |
| **浅色与深色两套配色都要** | 同一个下限。会挂的是 muted/subtle 这个角色，而且它通常只在两者之一上挂 |
| 根元素上的 `lang` | 设上它。没有它，读屏软件可能用英语语音去读 CJK |
| `focus-visible` | 绝不移除，绝不只用一个阴影来替代 |

## 8. Colour roles

一个控制台跑在它宿主应用设定的任何主题下。而一份文档是由拿到链接的那个人在浏览器里打开的，所以 `prefers-color-scheme: dark` 是一种正常情况，不是边界情形——而且没有它对应的取值，§7 的下限就无法核验。`reference-instance.md` §9 只有浅色，所以 colour roles 在这里**不**直接沿用。

**浅色**：用那份文件的 §9 表，外加一处覆盖。它的 `--ink-subtle` `#7d8894` 在 `--surface-sunken` 上测得 **3.21:1**——低于 §7 的下限，而本实例把这个角色用在表头与元数据上，控制台那边只把它用于非关键文字。改用 **`#5f6a76`**（4.90:1）。§9 里其余的一切按原样就能过下限。

**深色**：基础实例根本没有任何深色取值，所以整张表在这里给出。角色还是同一份清单；中性色仍然朝 accent 色相偏色。

| Token | 深色取值 |
|---|---|
| `--canvas` | `#12161b` |
| `--surface` | `#181d24` |
| `--surface-sunken` | `#1e242c` |
| `--ink` | `#e6ebf0` |
| `--ink-muted` | `#a3aeba` |
| `--ink-subtle` | `#96a2ae` |
| `--line` / `--line-soft` / `--line-strong` | `#2c343d` / `#232a32` / `#3d4650` |
| `--bg-hover` / `--bg-active` | `#1e242c` / `#242c35` |
| `--accent` / `--accent-ink` / `--accent-bg` | `#61a8f0` / `#8cc3f7` / `#16283c` |
| `--ok` / `--warn` / `--danger` | `#5cc48a` / `#d3a63c` / `#e88a82` |

阴影也需要它自己的深色取值——浅色那套叠加是针对白色表面调的，在深色表面上会消失。把 alpha 调高，把 spread 去掉。

**`--ink-subtle` 就是那个凭感觉定下、然后在两套配色里都挂掉的取值。**基础实例的 `#7d8894` 在浅色上测得 3.21:1；把它不加调整地移植到深色测得 4.33:1——两者都低于下限，而在作者眼里两者都完全可读。上面那两个覆盖值在表头上测得浅色 4.90、深色 6.01。去测你自己的，而不是把这几个搬过去：这个下限是你那些表面色的性质，不是这几个 hex 的性质。

## 9. 其余的一切

Radius family、elevation ladder、state matrix 与 numerals：`reference-instance.md`，未作改动。偏色中性色与靠线条分隔在这里同样适用，理由相同。

**位于 ramp 之下的那些东西，各自的 disposition。**这个 skill 的推导图把 radius、elevation、motion 与 state matrix 放在 type ramp 之下，而这里的 ramp 变了，所以每一个都欠一个答案，而不是直接沿用：

| ramp 之下的项 | disposition |
|---|---|
| Radius | **按判断改的，不是推导出来的。**`--r-lg` 6px → 8px。基础实例里没有任何规则把圆角绑到 ramp 上，所以没有东西需要重算；理由是本实例最外层的那些表面（页面卡片、通栏表格）比控制台的更大。记成一次判断，好让后来的读者知道它背后没有推导。嵌套规则本身没动：`outer − padding`，下限取 `--r-sm`——`--pad-card` 为 24px 时，一张 8px 的卡片里的子元素落在 3px 的下限上。 |
| Elevation | **沿用，并加了一级。**`reference-instance.md` §5 的第 0–3 级未作改动——它们依据的是表面与线条，不是字号。在 1 与 2 之间加了一级：sticky nav 级，因为一个有文字从它下面滚过去的 nav，需要比卡片（第 1 级）更强、比 popover（第 2 级）更弱的分隔。和其余各级一样是多层的：`0 0 0 1px rgba(28,33,40,.06), 0 1px 3px rgba(28,33,40,.07), 0 8px 24px -12px rgba(28,33,40,.14)`。 |
| Motion | **改了**——按 §4，是 140ms 而不是 120ms。 |
| State matrix | **检查过，没有变化。**这六种状态是按处理方式（边框、填充、描边）定义的，不是按尺寸，所以一条更大的 ramp 一个都动不了。唯一与尺寸耦合的那条——selected 可以把字重提一档但不能提字号——仍然成立，因为这条 ramp 的字重还是同样的 400/500/600。 |

Numerals 直接沿用：它定的是数字宽度与对齐，而 ramp 的字号不进入其中。**Colour roles 不直接沿用**——§8 为深色配色替换了它们，而那本身就是一次替换，不是一次继承。推导图把 colour roles 称作独立的，但那是基础实例的主张；这里记下的理由，是对着本实例核过的那一个。
